# 태양광 자산진단·유지보수 플랫폼 실현 가능성 검토

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 최종 수정일: 2026-08-31
- 주의: 이 문서는 계약 및 요구사항 확정 전 검토 의견이다. 샘플 검증, 상세 견적, 법적 검토와 계약을 대신하지 않는다.

## 1. 검토 결론

이 시스템은 기술적으로 구현 가능하다. 다만 제품의 핵심은 ‘AI 자동진단’보다는 `검사 접수 → 분석 보조 → 전문가 판정 → 보고서 발행 → 유지보수 연결`을 일관되게 관리하는 업무 플랫폼이다.

가장 큰 기술적 불확실성은 열화상 원본 형식, 방사온도 정보, 카메라 제조사 SDK와 열화상·가시광 이미지 매칭 품질이다. 이 항목은 실제 원본과 제조사 자료로 검증하기 전에는 일정·비용·진단 범위를 신뢰성 있게 확정하기 어렵다.

인버터 API는 유용하지만 제조사, 모델, 계정 권한과 설비 연결 정보를 확인해야 하므로 최초 MVP와 분리한 장기 과제로 두는 것이 적절하다. 정확한 범위와 견적을 산정하려면 샘플 이미지, 기존 보고서 양식, 예상 사용량, 사용자 역할과 실제 업무 절차를 먼저 확인해야 한다.

사용자가 현재 운영 중인 `Cloudflare + GitHub + Supabase` 조합은 초기 고정비와 운영 학습을 줄이는 현실적인 출발점이다. 다만 GitHub는 소스 기준, Cloudflare는 프론트엔드·도메인·엣지, Supabase는 인증·데이터·파일 책임으로 분리하고, 각 공급자의 고유 기능을 교체 가능한 경계에 두어야 한다. 카페24 등 별도 호스팅은 초기 필수 조건이 아니며 특정 서버·국내 지원·계약 요건이 생길 때 비교하는 편이 적절하다.

## 2. 확인된 내용

### 2.1 근거 자료

- 사용자 요청: 서비스 흐름, 핵심 원칙, MVP 후보, 장기 제외 범위와 기술 방향
- 사용자 추가 확인(2026-08-31): 현재 다른 서비스를 Cloudflare·GitHub·Supabase로 운영하고 있으며 신규 프로젝트도 향후 이전 가능성·호환성·확장성을 고려해야 함
- 「부천에너지이음 MVP 개발사 미팅」(2026-08-24): 실제 현장 3~5건을 접수부터 보고서·후속조치까지 처리한다는 목표, 필수 기능 묶음, 개발사 질문과 인계·검수 방향
- 기존 프로젝트 Markdown: 확정/추정 구분, 출처·한계, 재현·검증, 조직 격리, 보안·백업과 변경 기록 원칙

회의자료는 2쪽짜리 회의 체크리스트이며 승인된 요구사항서가 아니다. 예산·심의·보증 조건도 현재 적용 여부를 담당자가 재확인해야 한다.

### 2.2 구현 가능성이 높은 영역

- 고객사·발전소·설비·검사·일정과 담당자 관리
- 비공개 대용량 파일의 중단·재개 업로드, 체크섬과 메타데이터 관리
- 원본·미리보기·분석 파생물의 분리 보존
- 이미지 확대·주석·영역 표시와 전문가 수정 이력
- 역할별 전문가 검토, 승인과 감사 기록
- 한글 PDF 초안·승인·발행·개정과 고객 전용 다운로드
- 조직별 접근 통제, 내보내기, 백업·복원과 유지보수 후속 흐름

이 기능들은 일반적인 웹·파일·비동기 작업 기술로 구현할 수 있다. 다만 세부 난이도와 비용은 파일 규모, 역할 복잡도와 운영 품질 기준에 따라 달라진다.

### 2.3 별도 검증이 필요한 영역

- 카메라별 방사온도 원본 파싱과 정확한 온도 재계산
- 제조사 SDK의 서버 실행, 라이선스와 배포 제약
- 열화상·가시광 자동 매칭과 촬영 위치를 설비 위치에 연결하는 품질
- 이상 후보 알고리즘의 목표 유형, 오탐/누락과 설명 가능성
- 실제 대용량·동시 작업에서의 분석 시간과 비용
- 인버터 API의 데이터 범위, 호출 제한, 권한과 설비 연결 수준

## 3. 계약 전 기술 제안

### 3.1 적절한 제품 정의

최초 MVP는 자동 진단 제품이 아니라 전문가 업무를 안전하게 연결하는 ‘사람 중심 진단 운영 플랫폼’으로 정의하는 것이 현실적이다. 자동 분석의 가치는 전문가가 놓칠 수 있는 후보를 표시하고 검토 시간을 줄이는 데 있으며, 최종 책임과 고객 발행은 승인된 사람에게 둔다.

### 3.2 구현 방향

- 반응형 웹/PWA로 관리자·전문가·고객 흐름을 제공한다.
- 인증·업무 데이터·비공개 파일 권한은 조직 경계를 강제할 수 있는 백엔드에서 관리한다.
- 대용량 업로드는 재개 가능하게 하고 원본 체크섬과 파생 이력을 보존한다.
- 이미지 메타데이터 추출·분석은 별도 작업 서버에서 비동기로 처리한다.
- 자동 후보, 전문가 판정과 보고서 판본을 분리해 재현·감사를 가능하게 한다.
- 보고서는 HTML 기반 템플릿과 Chromium 계열 렌더링을 후보로 하되 한글 11pt/A4 검수를 자동·수동으로 수행한다.
- GitHub의 소스·잠금 파일·변경 이력을 재현 기준으로 삼고 Cloudflare·Supabase 전용 코드는 배포·데이터 어댑터에 격리한다.
- DB 변경 이력, Storage manifest·체크섬, 설정 inventory와 별도 작업 서버 컨테이너를 유지해 대체 환경으로 옮길 수 있게 한다.
- 계약 전에는 무료/저비용 구간을 사용할 수 있으나 실제 고객 원본을 받기 전 운영 플랜·별도 파일 백업·지출 한도와 장애 책임을 확정한다.

### 3.3 단계 권고

1. 샘플 원본·보고서·설비 연결도와 역할 흐름을 확보한다.
2. 제조사별 원본 파싱, 미리보기와 이미지 매칭 기술검증을 한다.
3. 필수·선택·제외 기능과 실제 자료 3~5건의 수용 기준을 합의한다.
4. 조직 격리·원본 보존·전문가 판정·보고서 발행을 핵심 MVP로 구현한다.
5. 유지보수 흐름을 계약 범위까지 연결하고 인계·복원 검수를 한다.
6. 인버터는 수동 자료로 가치를 확인한 뒤 단일 제조사 공식 API부터 별도 추진한다.

## 4. 주요 위험 평가

| 위험 | 현재 판단 | 영향 | 계약 전 조치 |
|---|---|---|---|
| 방사온도 정보/SDK | 높음 | 분석 범위·정확도·비용 변동 | 제조사별 원본·SDK 기술검증 |
| 이미지 자동 매칭 | 높음 | 잘못된 설비 연결과 전문가 재작업 | 실제 촬영 묶음으로 품질 측정, 수동 수정 필수 |
| 설비 위치·연결도 부족 | 높음 | 모듈/스트링 수준 해석 제한 | 자산대장·현장 위치 표준 합의 |
| 파일 규모·동시성 | 중간 | 저장·업로드·처리 비용 변동 | 3~5건의 실제 용량·시간 측정 |
| 역할·승인 정책 | 중간 | 발행 책임·재작업 위험 | 역할표와 개정·회수 시나리오 합의 |
| 조직 격리·파일 권한 | 중간/중요 | 고객 정보 노출 | 두 조직 교차 접근과 직접 URL 시험 |
| 인버터 API | 높음 | 연동 일정·데이터 가치 불확실 | 최초 MVP 분리, 거래처·권한 조사 |
| 운영·인계 조건 | 중간 | 계약 종료 후 운영 곤란 | 계정 명의, 소스·문서·백업 인계 명시 |
| Cloudflare·Supabase 과의존 | 중간 | 공급자 변경 시 재개발·중단·반출비용 증가 | 표준 빌드·PostgreSQL·컨테이너 우선, 어댑터 분리와 대체 환경 복원 시험 |

‘높음’은 구현 불가를 뜻하지 않고 계약 전 불확실성이 커 우선 검증해야 한다는 뜻이다.

## 5. 추가 확인이 필요한 내용

### 5.1 기술 자료

- 지원 카메라 제조사·모델·펌웨어와 열/가시광 원본 샘플
- 방사온도 정보, 제조사 SDK 문서·라이선스와 샘플 코드/응답
- 촬영 조건표, 설비 배치·연결도와 위치 식별 방식
- 기존 보고서 원본, 대표 진단과 정정·회수 사례

### 5.2 업무·사용량

- 역할별 사용자, 전문가 자격·배정·처리 기한과 승인 순서
- 검사당 파일 수·평균/최대 크기, 월 검사 수와 동시 작업
- 고객 원본 열람 범위, 보고서 판본·알림과 데이터 보존 정책
- 유지보수 업체 연결, 견적·작업 승인·완료 처리의 포함 범위

### 5.3 계약·운영

- 필수/선택 기능별 공수·비용·전제·제외사항과 월 운영비
- 일정, 단계별 지급, 검수 자료와 불합격·재검수 절차
- 기관 사전 승인, 선금보증, 지원금 계상과 계약 방식
- 소스·산출물 권리, 계정 명의, 2차 개발과 데이터 인계 권리
- 하자보수 기간·범위·응답시간, 이후 유지보수와 장애 대응
- 백업 주기, 복원 목표, 보안 사고와 계약 종료 시 파기·이관
- 현재 Cloudflare 제품·GitHub 저장소·Supabase 조직/프로젝트·도메인 소유권과 신규 프로젝트 분리 방식
- 공급자 이전 조건, 대체 환경, 허용 중단시간, 데이터 반출비용과 인증 사용자 전환 방식

## 6. 계약 체결 전 권고 조건

- 샘플 이미지 기술검증 결과를 제안서·견적의 전제로 명시한다.
- 필수 MVP, 선택 기능과 제외 기능을 기능별로 구분한다.
- 자동 분석은 후보 제시, 전문가는 최종 판정·발행 책임이라는 원칙을 수용 기준에 넣는다.
- 실제/대표 자료 3~5건의 종단 흐름과 역할·조직 격리·개정 이력을 검수한다.
- 원본·파생물·판정·보고서 판본의 보존과 재현 조건을 정한다.
- 운영 계정·소스·문서·백업·복원 절차의 소유권과 인계를 계약에 포함한다.
- 인버터 API는 별도 단계·견적으로 두고 공식 문서·권한 확인 전 확정하지 않는다.
- Cloudflare·Supabase 전용 기능 목록과 대체 구현 경계를 설계 산출물에 포함한다.
- 별도 시험 환경에 DB·Storage를 복원하고 대체 프론트엔드 호스트에서 종단 흐름을 확인하는 이전 리허설을 수용 기준에 넣는다.

## 7. 최종 판단

계약 전 조건부로 **추진 가능**하다. 먼저 ‘열화상 파일을 실제로 읽고 의미 있는 판단 자료를 만들 수 있는가’와 ‘현재 현장업무를 3~5건의 시나리오로 명확히 설명할 수 있는가’를 확인해야 한다. 이 두 가지가 확보되면 핵심 업무 플랫폼의 범위·비용·일정을 현실적으로 산정할 수 있다. 초기에는 현재 운영 경험이 있는 Cloudflare·GitHub·Supabase로 고정비를 낮추되, 대체 호스트 배포와 DB·Storage 복원 시험을 함께 준비하는 것이 적절하다. 확보되지 않은 상태에서 AI 정확도, 인버터 연동 또는 특정 공급자 고유 기능을 고정 범위로 계약하면 재작업과 비용 증가 위험이 크다.
