# MVP 계약·개발 계획 후보

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 최종 수정일: 2026-08-31
- 주의: 이 문서는 계약 및 요구사항 확정 전 단계 제안이다. 착수일, 기간, 인력, 비용과 납품 범위는 확정되지 않았다.

## 1. 확인된 내용

- 현재는 계약 전 검토 단계이며 이번 작업은 문서 준비만 수행한다.
- 최초 MVP는 자동 최종진단보다 접수, 원본 관리, 분석 보조, 전문가 판정, PDF 보고서와 후속 조치의 전체 흐름이 핵심이다.
- 회의자료는 실제 현장 자료 3~5건의 전 과정 검수, 기능별 견적, 일정표와 산출물·소스·계정·백업 절차 인계를 제안한다.
- 인버터 API는 최초 MVP 필수로 확정하지 않고 조사·수동 업로드 뒤 단일 제조사부터 검토한다.
- 사용자는 현재 다른 서비스를 `Cloudflare + GitHub + Supabase`로 운영하고 있다. 신규 프로젝트의 초기 인프라 후보는 이 경험을 활용하되 향후 다른 공급자로 옮길 수 있어야 한다.

## 2. 계약 전 기술 제안

### 2.1 단계와 의사결정 게이트

#### 0단계 - 계약 전 발견·타당성 확인

**목적:** 이미지 처리의 가장 큰 불확실성과 실제 업무 범위를 견적 전에 줄인다.

- 열화상·가시광 원본, 촬영표, 설비 연결도와 기존 보고서 확보
- 사용자·역할·승인·정정·유지보수 흐름 인터뷰
- 검사당 파일 수, 용량, 월 사용량과 보존 기간 조사
- 카메라 SDK·라이선스·분석 가능성 확인
- 필수/선택/제외 기능과 수용 기준 초안 합의

**게이트:** 샘플 원본을 읽을 수 있고, 실제 시나리오 3~5건과 책임 역할이 정의돼야 상세 견적의 신뢰도가 생긴다.

#### 1단계 - 제품·보안 설계

**목적:** 화면보다 먼저 조직 경계, 원본·파생물·판정·보고서 책임을 확정한다.

- 역할·권한표와 조직 격리 시나리오
- 정보 구조, 화면 흐름과 예외 처리
- 개념 모델을 실제 논리 설계로 전환
- 원본 보존, 체크섬, 업로드 재개와 작업 재시도 설계
- 보고서 템플릿, 승인·개정·회수 정책
- 운영 계정 소유권, 백업·복원과 인계 계획
- Cloudflare·GitHub·Supabase의 책임 경계, 교체 가능한 어댑터와 공급자 이전 계획

**게이트:** 요구사항, 화면 흐름, 보안·수용 기준과 변경 관리 방식에 발주/개발 양측이 동의한다.

#### 2단계 - 핵심 업무 기반

**목적:** 고객사·발전소·설비·검사 접수와 안전한 원본 업로드를 먼저 완성한다.

- 인증과 역할별 진입
- 고객사·발전소·설비 연결 구조 후보
- 검사 접수·일정·담당자 배정
- 재개 가능한 원본 업로드, 체크섬과 품질 상태
- 원본·미리보기·파생물 분리

**게이트:** 두 조직 이상의 교차 접근이 차단되고 큰 파일의 중단·재개·중복·손상 시나리오가 통과한다.

#### 3단계 - 이미지 검토와 전문가 판정

**목적:** 자동 후보를 전문가가 안전하게 검토·수정·확정할 수 있게 한다.

- 열/가시광 매칭 후보와 수동 수정
- 메타데이터·촬영 조건 품질 확인
- 분석 작업과 후보 영역 표시
- 확대·비교·주석과 수정 이력
- 전문가 배정, 진단·근거·권고 작성

**게이트:** 대표 샘플에서 분석 실패와 오매칭을 포함해 전문가가 최종 판단을 완료하고 이력을 재현할 수 있다.

#### 4단계 - 보고서와 고객 제공

**목적:** 승인된 판정을 읽기 쉬운 고객 보고서로 안전하게 발행한다.

- 보고서 초안·검토·승인·발행·개정/회수
- 한글 PDF, 최소 11pt와 A4 레이아웃 검증
- 고객 전용 조회·다운로드
- 알림과 만료 파일 링크 후보

**게이트:** 계약된 판본 정책과 권한에 따라 고객이 올바른 보고서를 다운로드하고 과거/회수 판본이 정책대로 처리된다.

#### 5단계 - 유지보수 후속 흐름·파일럿

**목적:** 권고가 실제 조치 결과로 이어지는지 전 과정에서 검증한다.

- 유지보수 요청, 담당/사업자 연결
- 범위에 포함된 견적·작업 진행
- 조치 전·후 사진과 완료 확인
- 실제 또는 비식별 자료 3~5건의 종단 검수
- 운영 문서, 교육, 백업·복원과 계정 인계
- 깨끗한 GitHub clone 재빌드, 별도 시험 프로젝트 복원과 대체 프론트엔드 호스트 배포 연습

**게이트:** `접수 → 업로드 → 표시 → 전문가 검토 → 보고서 발행 → 고객 다운로드 → 후속 조치 기록`이 권한·이력·복구 조건을 포함해 완료된다.

단계 번호는 업무 선후관계 제안이며 계약상 회차나 고정 일정이 아니다.

### 2.2 MVP 산출물 후보

- 확정 요구사항서와 필수/선택/제외 범위표
- 사용자 역할·업무 흐름·권한표
- 화면 설계와 오류/예외 흐름
- 시스템 구성, 실제 논리 데이터 설계와 파일 보존 설계
- 소스, 정확한 의존성 잠금 파일과 재현 가능한 빌드·배포 절차
- 자동·수동 시험 결과, 보안·조직 격리와 종단 검수 기록
- 운영자·전문가·고객 사용 안내
- 운영 계정, 도메인, 저장소, 데이터 내보내기와 백업·복원 절차
- 공급자별 설정 inventory, 비밀값 없는 환경설정 예시, DB 변경 이력과 Storage 객체 manifest
- 대체 프론트엔드 호스트·별도 DB/Storage 시험 환경으로 옮기는 이전·검증·롤백 안내
- 하자보수·유지보수와 장애 연락 절차

산출물의 형식, 편집 가능한 원본, 소유권과 인계 시점을 계약서에 명시한다.

### 2.3 견적 구조 권고

- 필수 MVP와 선택 기능을 분리한다.
- 기능 또는 단계별 공수·비용·전제·제외사항을 표시한다.
- 공급가액과 부가세, 개발비와 월 운영비·유지보수비를 분리한다.
- 저장소, 이미지 처리, 알림, 외부 API 등 사용량 기반 비용의 산정 기준을 표시한다.
- 단계별 지급 조건을 검수 결과와 연결한다.
- 범위 변경 시 일정·비용·수용 기준의 변경 승인 절차를 정한다.

회의자료에는 초기 예산 760만원, 1000만원 범위의 확대 검토, 500만원 이상 외주용역 심의와 선금보증 관련 메모가 있다. 이는 계약 확정 조건이 아니므로 현재 지원기관 규정, 부가세·지원금 계상과 직접계약 구조를 담당자가 다시 확인해야 한다.

### 2.4 우선순위 제안

**반드시 먼저:** 샘플 원본 검증, 역할·승인, 조직 격리, 원본 무결성, 전문가 판정, 보고서 발행.

**MVP 포함 여부를 계약에서 결정:** 일정 관리의 깊이, 고객 원본 열람, 알림 채널, 유지보수 업체 화면, 견적·완료 승인.

**후순위:** 단일 제조사 인버터 API, 여러 제조사 공통화, 실시간 관제와 상관분석.

**제외 권고:** AI 단독 확정, 신규 모델 학습, 자동입찰·결제·정산, 네이티브 앱, 자동 예지 정비.

### 2.5 주요 위험과 완화

| 위험 | 영향 | 계약 전 완화 |
|---|---|---|
| 방사온도 원본/SDK 미지원 | 온도 분석 범위 축소, 일정·비용 증가 | 제조사별 원본과 SDK 라이선스 사전 검증 |
| 이미지 매칭 품질 부족 | 잘못된 설비 판단 위험 | 신뢰도 표시, 수동 수정, 촬영 절차 개선 |
| 파일 규모 과소평가 | 업로드·저장·처리 비용 증가 | 실제 3~5건으로 용량·시간 측정 |
| 역할·승인 불명확 | 재작업과 책임 공백 | 역할표와 발행·개정 시나리오 합의 |
| 조직 격리 누락 | 중대한 정보 노출 | 두 조직 교차 접근을 수용 시험에 포함 |
| 보고서 기준 미확정 | 템플릿 재작업 | 기존 보고서와 필수 문구·서명 사전 확보 |
| 운영 계정·권리 불명확 | 인계·2차 개발 차질 | 조합/운영 주체 명의와 권리·인계 계약 명시 |
| 인버터 API 불확실 | 연동 일정·비용 산정 실패 | 최초 MVP에서 분리, 단일 제조사 검증 후 결정 |
| 공급자 고유 기능 과의존 | Cloudflare·Supabase 이전 비용과 중단 증가 | 어댑터 분리, 표준 PostgreSQL·컨테이너·객체 manifest와 대체 환경 복원 시험 |

### 2.6 초기 고정비와 확장 단계

#### 계약 전 시제품

- 현재 운영 경험이 있는 GitHub·Cloudflare·Supabase를 우선 활용한다.
- 카페24 등 별도 호스팅 구매는 기본 범위에 넣지 않는다.
- Supabase 무료 구간은 가짜·비식별 소량 자료의 화면·흐름 검증에만 사용한다.
- 현재 공식 플랜의 일시정지, 업로드 크기, 저장·전송량, 자동 백업과 지원 조건을 착수 시 다시 확인한다.

#### 실제 고객 자료 파일럿

- 첫 실제 원본을 받기 전에 운영 플랜, 저장량·전송량 예산, 별도 Storage 백업과 장애 책임을 확정한다.
- 지출 한도, 사용량 알림과 월별 비용 점검을 설정한다.
- 무료 플랜의 제약을 우회하기 위해 파일을 쪼개거나 품질을 낮추지 않는다. 요구사항에 맞는 유료 플랜 또는 다른 저장소를 선택한다.
- 원본 3~5건의 실제 용량·처리 시간·다운로드량을 측정해 정식 운영 비용을 다시 산정한다.

#### 정식 운영과 이전 판단

- 비용, 성능, 데이터 지역, 장애·지원, 계약·규정 또는 기능 요구가 기준을 넘을 때 공급자 이전을 검토한다.
- 카페24 VPS나 다른 클라우드는 특정 런타임, 국내 지원·청구 또는 자체 운영 요구가 있을 때만 비교한다.
- 이전은 기존 환경을 즉시 해지하는 방식이 아니라 `백업 → 시험 복원 → 병행 검증 → DNS/트래픽 전환 → 롤백 대기 → 기존 키 폐기` 순서로 계획한다.

## 3. 추가 확인이 필요한 내용

### 3.1 범위·업무

- 실제 MVP에서 유지보수 요청·견적·작업을 어디까지 포함할지
- 고객·촬영자·전문가·승인자의 수와 역할 겸임
- 처리 기한, 재촬영, 보고서 정정·회수와 고객 알림 절차
- 실제 자료 3~5건의 선정, 비식별 여부와 합격 기대 결과

### 3.2 일정·비용

- 착수 가능일, 필수 납기와 단계별 검토 기간
- 개발사 투입 인력·역할, 외부 영상분석 전문 인력
- 저장·분석·PDF·알림 월 사용량과 운영비
- 기관 사전 승인, 선금보증, 지급·검수와 증빙 조건
- Cloudflare·Supabase의 시제품/파일럿/운영 플랜과 사용량 초과·반출 비용

### 3.3 권리·운영

- 소스·문서·디자인·분석 로직과 데이터의 권리 귀속
- 저장소·도메인·클라우드·외부 API 계정의 명의
- 배포·장애 대응·백업·복원과 보안 사고 책임
- 하자보수 기간, 범위, 응답시간과 이후 유지보수 단가
- 현재 Cloudflare 제품과 배포 방식, 신규 계정 분리 여부와 도메인/DNS 소유권
- 공급자 이전을 시작할 기준, 허용 중단시간, 데이터 반출·복원과 인증 사용자 전환 방식

## 4. 계약 전 회의에서 받을 답변

1. 개발사가 이해한 사용자와 전체 업무 흐름
2. 실제 원본 기준 가능·어려운 기능과 제외사항
3. 필수/선택 기능별 공수·가격·전제
4. 기술·서버 구성과 월 운영비
5. 계정·데이터·소스·산출물 인계 방식
6. 실제 자료 종단 검수와 합격 기준
7. 유사 실적, 투입 인력, 하자보수와 유지보수 조건
8. 일정표, 단계별 지급과 범위 변경 절차
9. Cloudflare·Supabase 종속 기능 목록과 대체 환경 이전·롤백·비용 산정 방식
