# 향후 검증 계획 체크리스트

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 최종 수정일: 2026-08-31
- 주의: 이 문서는 계약 및 요구사항 확정 전 테스트 계획이다. 아래 항목은 아직 수행하거나 통과하지 않았으며, 체크 표시는 구현 후 증거와 함께 기록한다.

## 1. 확인된 내용

- 최종 검수는 화면이 열리는지보다 실제 자료가 접수부터 고객 보고서·후속 조치까지 완료되는지를 기준으로 해야 한다.
- 회의자료는 실제 자료 3건, 사용자 요청은 실제/대표 자료 3~5건의 종단 흐름 검토를 제시한다. 정확한 표본과 합격 기준은 계약에서 확정한다.
- 자동 분석 결과가 아니라 전문가의 최종 판정과 승인이 보고서 발행의 기준이다.
- 다중 조직 격리, 원본 무결성, 수정·발행 이력과 백업·복원이 핵심 검증 대상이다.

## 2. 계약 전 기술 제안

### 2.1 테스트 증거 원칙

- 각 항목에 환경, 계정 역할, 조직, 샘플, 실행일과 결과를 기록한다.
- 실패가 예상되는 보안·오류 시나리오도 실제로 시도하고 거부 결과를 남긴다.
- PASS는 기대 결과와 증거가 일치할 때만 표시한다.
- 실제 고객 데이터 대신 승인된 비식별 또는 시험 자료를 우선한다.
- 운영 검증에서 불필요한 저장·발행·알림은 최종 실행 직전에 안전하게 중단한다.

### 2.2 최소 테스트 구성 후보

- 서로 다른 고객 조직 2개 이상
- 각 조직의 관리자와 고객 사용자
- 촬영 담당자, 전문가와 승인자(겸임 여부에 따라 별도 계정)
- 유지보수 담당자/사업자 계정(범위에 포함될 경우)
- 정상·이상·경계·짝 누락·오매칭·손상 사례가 포함된 검사 3~5건
- 작은 파일, 최대 크기 근접 파일과 다수 파일 묶음
- 발행·개정·회수 가능한 보고서 예시

## 3. 검증 체크리스트

### 3.1 조직 격리와 역할 권한

- [ ] 두 개 이상의 고객 조직을 만들고 각 조직의 고객사·발전소·검사·보고서가 상호 노출되지 않는지 확인한다.
- [ ] 조직 A에서 만든 데이터가 조직 B의 목록·검색·자동완성·통계·알림에 나타나지 않는지 확인한다.
- [ ] 역할별 조회·생성·수정·진단·승인·발행·회수·내보내기 권한이 합의된 권한표와 일치하는지 확인한다.
- [ ] 고객 사용자가 전문가 화면·승인 전 초안·허용되지 않은 원본에 접근하지 못하는지 확인한다.
- [ ] 전문가가 배정되지 않았거나 권한이 없는 검사를 수정·확정하지 못하는지 확인한다.
- [ ] 직접 URL이나 대상 ID를 다른 조직 값으로 바꿔도 조회·수정·삭제·다운로드가 차단되는지 확인한다.
- [ ] 조직 정보를 해석할 수 없는 요청이 다른 조직의 기본값이 아니라 거부 또는 빈 결과가 되는지 확인한다.
- [ ] 역할 회수·조직 탈퇴·계약 종료 뒤 기존 세션과 열린 화면에서 권한이 적시에 사라지는지 확인한다.

### 3.2 인증·세션·파일 접근

- [ ] 로그인, 로그아웃, 만료 세션, 비밀번호/인증 복구와 허용된 복귀 경로를 확인한다.
- [ ] 비공개 원본·파생물·보고서가 익명 요청으로 노출되지 않는지 확인한다.
- [ ] 서명 URL이 만료된 뒤 다운로드가 실패하고, 권한이 있으면 안전하게 재발급되는지 확인한다.
- [ ] 파일 권한을 회수한 뒤 아직 만료되지 않은 링크와 브라우저 캐시에서 접근이 차단되는지 정책대로 확인한다.
- [ ] 파일명, 미리보기, 오류 메시지와 내보내기 목록에서 다른 조직 정보가 새지 않는지 확인한다.
- [ ] Supabase 사용 시 RLS와 Data API GRANT를 별도로 점검하고, 프론트엔드 필터를 제거해도 접근이 차단되는지 확인한다.
- [ ] 브라우저에 비밀 키·외부 API 토큰이 포함되지 않고 네트워크·로그·소스맵에 노출되지 않는지 확인한다.

### 3.3 대용량 업로드와 원본 무결성

- [ ] 대용량 업로드 중 네트워크를 끊고 같은 파일을 중단 지점부터 재개할 수 있는지 확인한다.
- [ ] 브라우저 종료·재로그인·재시도 후 허용된 업로드 세션이 안전하게 복구되는지 확인한다.
- [ ] 동일 파일을 중복 업로드했을 때 체크섬으로 중복 후보를 감지하고 업무적으로 올바르게 처리하는지 확인한다.
- [ ] 다른 검사에서 동일 체크섬 파일을 제출한 합법적 사례를 잘못 삭제하거나 공유하지 않는지 확인한다.
- [ ] 최대 파일 수·최대 크기와 동시 업로드에서 진행률, 취소, 재시도와 완료 판단이 정확한지 확인한다.
- [ ] 잘못된 확장자, MIME 불일치, 지원하지 않는 형식과 손상된 파일을 안전하게 거부·격리하는지 확인한다.
- [ ] 업로드 원본과 저장된 원본의 크기·체크섬이 일치하고 미리보기 생성이 원본을 바꾸지 않는지 확인한다.
- [ ] 중복 클릭·네트워크 재전송이 파일·검사·작업을 불필요하게 여러 번 만들지 않는지 확인한다.

### 3.4 열화상·가시광과 메타데이터

- [ ] 지원 카메라별 원본에서 합의된 방사온도 정보와 메타데이터를 읽고 출처를 구분하는지 확인한다.
- [ ] 방사온도 정보가 없는 파일을 온도 분석 가능 원본으로 잘못 표시하지 않는지 확인한다.
- [ ] 열화상·가시광 짝 누락을 감지하고 전문가 검토/보완 흐름으로 보내는지 확인한다.
- [ ] 잘못된 자동 매칭과 복수 후보를 신뢰도와 함께 표시하고 사람이 수동 수정·해제할 수 있는지 확인한다.
- [ ] 수동 매칭 수정 전후, 수정자, 시점과 사유가 보존되는지 확인한다.
- [ ] 촬영 시각, 타임존, 위치, 카메라, 거리·각도, 날씨·일사량 등 필수 조건의 누락·이상값을 표시하는지 확인한다.
- [ ] 장비 시간 오차, 중복 파일명, 폴더 순서 변경과 GPS 부재에서도 오매칭을 자동 확정하지 않는지 확인한다.

### 3.5 분석 보조와 이미지 주석

- [ ] 분석 성공·실패·대기·재시도와 사용한 입력·처리 버전을 추적할 수 있는지 확인한다.
- [ ] 같은 요청의 재시도가 중복 결과를 무제한 생성하지 않고, 재실행 결과는 이전 결과와 구분되는지 확인한다.
- [ ] 온도 이상·고장 의심 영역이 원본 좌표와 확대/축소 상태에서 정확히 정렬되는지 확인한다.
- [ ] 이미지 확대, 이동, 팔레트/표시 전환과 열·가시광 비교가 주요 기기에서 동작하는지 확인한다.
- [ ] 점·영역·텍스트 주석의 생성, 수정, 삭제와 수정 이력이 정확히 남는지 확인한다.
- [ ] 자동 후보를 전문가가 채택·수정·병합·분리·기각하고 원래 후보와 관계를 추적할 수 있는지 확인한다.
- [ ] 분석 경고·신뢰도·자료 한계가 고장 확정처럼 오해되지 않게 표시되는지 확인한다.

### 3.6 전문가 검토와 승인

- [ ] 전문가 배정, 재배정, 처리 기한과 알림이 합의된 업무 흐름대로 동작하는지 확인한다.
- [ ] 전문가는 원본, 가시광 짝, 촬영 조건, 설비 정보와 분석 후보를 함께 확인할 수 있는지 확인한다.
- [ ] 최종 진단, 판정 근거, 불확실성, 코멘트와 조치 권고의 필수 입력을 확인한다.
- [ ] 전문가 검토 완료 전 보고서 승인·발행이 차단되는지 확인한다.
- [ ] 승인자가 승인 또는 수정 요청을 하고 작성자와 승인자 이력이 분리되는지 확인한다.
- [ ] 승인 후 판정 변경이 무음 덮어쓰기가 아니라 개정·재승인 절차로 이어지는지 확인한다.

### 3.7 보고서

- [ ] 보고서 초안, 검토, 승인, 발행, 개정과 회수가 서로 구분되고 허용된 전이만 가능한지 확인한다.
- [ ] 발행 보고서가 올바른 발전소·검사·원본·분석 실행·전문가 판정과 연결되는지 확인한다.
- [ ] 개정 시 과거 발행본을 덮어쓰지 않고 새 판본과 변경 사유·승인을 보존하는지 확인한다.
- [ ] 회수된 보고서의 고객 열람·다운로드·대체 안내가 계약된 정책과 일치하는지 확인한다.
- [ ] 고객은 자신의 조직에 발행된 보고서만 목록·검색·다운로드할 수 있는지 확인한다.
- [ ] 한글 PDF 글꼴이 누락·대체·깨짐 없이 표시되는지 확인한다.
- [ ] 제목·본문·표·각주·페이지 번호 등 모든 텍스트가 최소 11pt인지 확인한다.
- [ ] A4에서 긴 표, 많은 이미지, 주석·서명, 긴 고객명과 페이지 넘침·잘림·겹침이 없는지 확인한다.
- [ ] 보고서 생성 재시도와 중복 발행 클릭이 동일 판본을 여러 번 발행·알림하지 않는지 확인한다.

### 3.8 모바일·접근성·화면 안정성

- [ ] 저사양 모바일에서 긴 검사 목록, 큰 이미지와 보고서 조회가 사용 가능한지 확인한다.
- [ ] 실제 iOS Safari에서 업로드 선택, 중단·재개, 이미지 제스처와 PDF 다운로드를 확인한다.
- [ ] 키보드만으로 핵심 흐름을 수행하고 포커스 위치·레이블·오류 안내를 이해할 수 있는지 확인한다.
- [ ] 중첩 모달의 z-index, 포커스 가둠/복귀와 배경 스크롤 잠금이 올바르게 동작하는지 확인한다.
- [ ] 모달·드롭다운·이미지 주석 도구가 작은 화면에서 잘리거나 닫을 수 없는 상태가 되지 않는지 확인한다.
- [ ] 느린 네트워크, 화면 회전, 백그라운드 복귀와 브라우저 새로고침에서 입력 손실·중복 제출을 확인한다.

### 3.9 유지보수 후속 업무

- [ ] 진단의 조치 권고에서 유지보수 요청을 만들고 대상 항목이 정확히 연결되는지 확인한다.
- [ ] 요청부터 범위 확인, 담당/사업자 연결, 견적·계획, 작업, 완료/부분 완료·보류까지 상태 흐름을 확인한다.
- [ ] 조치 전·후 사진과 완료 결과가 올바른 요청·발전소·권고에 연결되는지 확인한다.
- [ ] 외부 사업자가 허용된 최소 정보만 보고 다른 고객 원본·보고서에 접근하지 못하는지 확인한다.
- [ ] 취소, 거절, 무응답, 재작업과 부분 완료가 진단 결과를 잘못 변경하지 않는지 확인한다.
- [ ] 고객 또는 승인 담당자의 완료 확인이 필요한 경우 권한·감사 이력이 남는지 확인한다.

### 3.10 알림·내보내기·감사

- [ ] 알림 대상·내용·시점이 조직과 역할에 맞고 다른 고객 정보가 포함되지 않는지 확인한다.
- [ ] 중복 이벤트, 재시도와 공급자 장애에서 중복 알림 또는 영구 누락을 탐지할 수 있는지 확인한다.
- [ ] 데이터 내보내기가 요청 조직·기간·대상만 포함하고 만료 후 접근되지 않는지 확인한다.
- [ ] 원본 업로드, 매칭 수정, 전문가 판정, 승인·발행·개정·회수와 권한 변경의 감사 이력을 조회할 수 있는지 확인한다.
- [ ] 감사 로그에 비밀 키·토큰·서명 URL 전체와 불필요한 민감정보가 저장되지 않는지 확인한다.

### 3.11 백업·복원과 장애

- [ ] 업무 데이터, 원본/파생 파일, 보고서와 핵심 설정의 백업 범위를 확인한다.
- [ ] 백업 파일의 무결성, 암호화, 접근 권한과 보존 기간을 확인한다.
- [ ] 별도 시험 환경에서 백업을 복원하고 조직 격리·파일 관계·보고서 판본이 유지되는지 확인한다.
- [ ] 복원 시점의 진행 중 업로드·분석·보고서 작업이 중복 또는 유실 없이 정리되는지 확인한다.
- [ ] 합의된 복구 시간과 허용 데이터 손실 목표를 실제 복원 기록으로 검증한다.
- [ ] 외부 이미지 작업 서버·알림·저장소 장애 후 재시도와 사용자 안내를 확인한다.

### 3.12 인버터 연동(해당 단계에서 수행)

- [ ] API 토큰 만료와 권한 회수 시 수집이 안전하게 중단되고 재인증 절차가 동작하는지 확인한다.
- [ ] 잘못된 조직/발전소 자격증명으로 다른 고객 데이터를 수집하지 않는지 확인한다.
- [ ] 호출 제한 응답, 일시 장애와 네트워크 오류에서 공식 정책에 맞게 대기·재시도하는지 확인한다.
- [ ] 동일 기간의 중복 수집, 지연 도착과 역순 데이터가 중복·잘못된 최신값을 만들지 않는지 확인한다.
- [ ] 누락값, 비정상 단위, 타임존 차이와 장비 시계 오류를 감지·표시하는지 확인한다.
- [ ] 인버터·게이트웨이·MPPT·스트링 장비 교체와 재배선이 과거 데이터 관계를 바꾸지 않는지 확인한다.
- [ ] 제조사 오류 코드 원문과 해석, 원시 응답과 정규화 결과를 재현할 수 있는지 확인한다.
- [ ] 인버터 데이터가 열화상 후보를 자동 고장 확정으로 바꾸지 않고 전문가 보조 근거로만 사용되는지 확인한다.

### 3.13 종단 수용 검수

- [ ] 계약에서 정한 실제/대표 자료 3~5건을 접수한다.
- [ ] 원본 업로드·체크섬·짝 확인과 분석 후보 표시를 완료한다.
- [ ] 전문가가 후보를 검토·수정하고 최종 진단·권고를 작성한다.
- [ ] 승인자가 보고서를 검토해 발행한다.
- [ ] 각 고객 계정에서 자신의 PDF만 조회·다운로드한다.
- [ ] 유지보수 요청과 조치 결과를 계약 범위까지 기록한다.
- [ ] 소스·운영 계정·문서·내보내기·백업과 복원 절차 인계를 확인한다.
- [ ] 각 단계의 실패·수정·재시도와 감사 이력을 재현한다.

### 3.14 Cloudflare·GitHub·Supabase 호환성과 이전 가능성

- [ ] 새 작업 폴더에서 GitHub 저장소를 깨끗하게 clone하고 문서에 적힌 정확한 런타임·잠금 파일만으로 같은 빌드 산출물을 재현하는지 확인한다.
- [ ] Cloudflare 배포 설정과 애플리케이션 업무 코드가 분리돼 있고, 배포 제공자 식별자·주소가 코드에 하드코딩되지 않았는지 확인한다.
- [ ] 같은 프론트엔드 빌드를 대체 정적/엣지 호스트 시험 환경에 배포하고 핵심 업무 코드 수정 없이 환경설정만으로 동작하는지 확인한다.
- [ ] 대체 호스트에서 직접 URL 새로고침, 404 처리, 보안 헤더, CORS, 인증 콜백과 로그아웃 복귀가 정상인지 확인한다.
- [ ] 사용자 소유 도메인을 유지한 채 시험 원본 대상으로 전환하고, DNS 캐시·HTTPS 인증서·롤백 시간을 측정한다.
- [ ] 빈 시험 프로젝트에 저장소의 변경 이력과 설정 문서만으로 데이터 구조를 재현하고 Data API 권한과 RLS를 다시 검증한다.
- [ ] DB 내보내기·복원 후 조직별 행 수, 핵심 관계, 시간대, 보고서 판본과 감사 이력이 원본과 일치하는지 확인한다.
- [ ] Storage 객체를 반출·재업로드하고 manifest의 객체 수·크기·형식·체크섬·조직 소속이 전부 일치하는지 확인한다.
- [ ] DB 백업만 복원했을 때 Storage 파일이 자동 복원된다고 가정하지 않고 파일 백업·복원 절차를 별도로 수행한다.
- [ ] 만료 서명 URL·일회성 업로드 URL을 이전 데이터로 복사하지 않고 새 환경에서 권한 확인 후 재발급하는지 확인한다.
- [ ] 인증 공급자를 바꾸거나 새 Supabase 프로젝트로 옮기는 시험에서 사용자·조직·역할 관계와 강제 재로그인/비밀번호 재설정 정책을 확인한다.
- [ ] Supabase 클라이언트·Storage·Queue와 Cloudflare 고유 호출이 교체 가능한 어댑터에 모여 있고 핵심 업무 규칙에 흩어지지 않았는지 확인한다.
- [ ] 이미지 처리 작업을 표준 컨테이너로 다른 작업 환경에서 실행하고 동일 입력 체크섬에서 추적 가능한 결과를 생성하는지 확인한다.
- [ ] 기존·신규 환경을 병행한 상태에서 데이터 동결 또는 증분 동기화, 최종 전환, 검증 실패 시 롤백 절차를 연습한다.
- [ ] 공급자 이전에 필요한 데이터 반출 시간·전송 비용·운영 중단시간과 담당자를 기록한다.
- [ ] 저장소·도메인·Cloudflare·Supabase·작업 서버 계정의 소유자, 복구 관리자와 비밀값 재발급 목록이 최신인지 확인한다.
- [ ] 이전 완료 후 사용하지 않는 키·세션·웹훅·배포·캐시와 서비스 계정이 폐기됐는지 확인한다.
- [ ] 예상 조직·파일·분석 작업을 단계적으로 늘려 현재 플랜의 저장·전송·동시성 한계와 확장 시점을 확인한다.
