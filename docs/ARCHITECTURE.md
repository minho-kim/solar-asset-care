# 계약 전 시스템 아키텍처 제안

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 최종 수정일: 2026-08-31
- 주의: 이 문서는 계약 및 요구사항 확정 전 기술 제안이다. 제품·서비스 선택, 배포 구조와 용량은 확정되지 않았다.

## 1. 확인된 내용

- 기존 홈페이지나 ERP에 붙이는 기능이 아니라 별도 신규 시스템이다.
- 열화상·가시광 원본, 화면용 미리보기, 분석 파생물, 전문가 판정과 보고서 판본을 구분해야 한다.
- 자동 분석은 최종 판정자가 아니며 전문가 검토가 필수다.
- 다중 고객 조직을 지원할 가능성이 있으므로 조직별 데이터와 파일 격리를 고려해야 한다.
- 대용량 업로드, 이미지 분석과 보고서 생성은 실패·재시도·중복 실행을 고려해야 한다.
- 사용자는 현재 다른 서비스를 `Cloudflare + GitHub + Supabase` 조합으로 운영하고 있다. 이 경험은 신규 프로젝트의 초기 구성과 운영 절차를 검토할 때 참고할 수 있다.

## 2. 계약 전 기술 제안

### 2.1 논리 구성

```text
사용자 웹/PWA
  ├─ 운영·전문가 업무 화면
  ├─ 고객 전용 화면
  └─ 재개 가능한 원본 업로드
        │
        ▼
인증·업무 API·권한 계층
  ├─ 조직/역할 기반 접근 통제
  ├─ 검사·설비·진단·보고서 업무 데이터
  ├─ 비공개 파일 접근 승인
  └─ 작업 요청·알림 조정
        │
        ├───────────────┐
        ▼               ▼
비공개 파일 저장소      비동기 작업/큐
  ├─ 변경 불가 원본       ├─ 미리보기 생성
  ├─ 화면용 미리보기      ├─ 메타데이터 추출
  ├─ 분석 파생물          ├─ 분석 보조
  └─ 보고서 판본          └─ 보고서 생성
                            │
                            ▼
                       별도 이미지 작업 서버
```

구현 시 모든 흐름이 단일 제품처럼 보이더라도, 권한 확인·원본 보존·무거운 작업·보고서 발행 책임은 분리하는 편이 안전하다.

### 2.2 초기 배포 기준선 후보

- **GitHub:** 소스, 검증된 의존성 잠금 파일, 변경 이력과 배포 정의의 기준 저장소
- **Cloudflare:** 사용자 웹의 정적/엣지 배포, 사용자 소유 도메인·DNS와 필요한 보안 헤더 계층 후보
- **Supabase:** 인증, PostgreSQL 업무 데이터, 비공개 Storage와 짧은 작업 조정 계층 후보
- **별도 작업 서버:** 열화상 메타데이터 처리, 분석 보조와 PDF처럼 실행 시간이 길거나 전용 라이브러리가 필요한 작업

현재 운영 경험을 재사용하면 초기 학습·운영 비용을 줄일 수 있다. 다만 신규 프로젝트의 Cloudflare 계정/영역, GitHub 저장소와 Supabase 조직/프로젝트는 기존 운영 서비스와 분리하고 소유자·관리자·비용 책임을 문서화한다. 정확한 Cloudflare 제품, 빌드 런타임, 배포 제한과 Supabase 플랜은 착수 시점의 공식 문서를 다시 확인한다.

계약 전 화면 시제품은 허용되는 무료/저비용 구간을 사용할 수 있다. 실제 고객 원본을 받는 파일럿부터는 프로젝트 일시정지, 업로드 한도, 저장·전송량, 자동 백업, 보안 지원과 장애 대응 수준이 계약 조건에 맞는지 확인한 뒤 운영 플랜을 선택한다. 카페24 등 별도 호스팅은 초기 필수 구성으로 두지 않고 국내 결제·지원, 특정 서버/런타임 또는 계약상 요구가 생길 때 비교한다.

### 2.3 프론트엔드 후보

- Next.js App Router, React, TypeScript
- Tailwind CSS와 shadcn/ui 또는 동등한 접근성 기반 UI 구성
- `react-konva` 또는 동등한 이미지 확대·주석 도구
- Uppy/TUS 계열 또는 동등한 재개 가능한 업로드
- 반응형 웹/PWA, 저사양 모바일과 실제 iOS Safari 고려

브라우저는 사용자 상호작용과 화면 표시를 담당한다. 외부 API 비밀정보, 비밀 키와 장기 토큰을 보관하지 않는다. 큰 파일을 애플리케이션 서버 메모리로 중계할지 저장소로 직접 보낼지는 보안·재개·비용 검증 후 정한다.

### 2.4 업무 백엔드 후보

- Supabase Postgres: 검사·설비·진단·보고서와 감사 관계 데이터 후보
- Supabase Auth: 사용자 인증과 세션 후보
- Supabase Storage: 조직별 권한이 적용되는 비공개 원본·파생물·보고서 후보
- Supabase Queues: 이미지·보고서·알림 작업 전달 후보
- Edge Functions: 짧은 요청, 웹훅, 알림과 작업 조정 후보

Supabase는 제안일 뿐이다. 사용한다면 조직 경계를 RLS로 강제하고, 필요한 역할에만 Data API 권한을 부여하며, 명확한 공개 목적이 없는 익명 접근을 허용하지 않는 방향으로 검토한다. 무거운 영상 처리를 Edge Function 안에서 수행하지 않는다.

### 2.5 이미지 처리 후보

- Python/FastAPI 기반 별도 작업 서비스
- OpenCV와 검증된 분석 라이브러리
- 지원 카메라 제조사 SDK 또는 방사온도 메타데이터 파서
- Cloud Run 또는 동등한 격리 실행 환경

작업은 원본을 읽기 전용으로 사용하고 결과를 새 파생물로 만든다. 작업 요청에는 중복 실행을 식별할 수 있는 논리 키가 필요하며, 결과에는 사용 입력, 처리 버전, 시간, 성공/실패와 품질 정보를 연결한다. 구체 키와 필드는 계약 후 설계한다.

### 2.6 보고서 생성 후보

- 승인된 진단 데이터를 HTML 템플릿에 결합
- Playwright/Chromium 또는 동등한 렌더러로 PDF 생성
- 한글 글꼴 포함, 모든 텍스트 최소 11pt
- A4에서 표·이미지·주석·서명·페이지 번호의 넘침과 잘림 확인
- 발행본은 불변 판본으로 보존하고 개정 시 새 판본 생성

### 2.7 주요 데이터 흐름

#### 원본 업로드

1. 사용자의 조직·검사·업로드 권한을 확인한다.
2. 업로드 세션을 만들고 중단·재개 상태를 관리한다.
3. 완료된 파일의 크기·체크섬·형식과 기본 메타데이터를 확인한다.
4. 원본을 비공개 영역에 보존하고 미리보기·분석 작업을 별도로 요청한다.
5. 클라이언트의 중복 클릭이나 네트워크 재시도에도 같은 원본이 무제한 복제되지 않게 한다.

#### 분석과 전문가 판정

1. 작업자가 승인된 입력만 읽는다.
2. 분석 후보와 파생 시각화를 새 결과로 저장한다.
3. 전문가는 원본·파생물·설비·촬영 정보를 함께 본다.
4. 전문가의 최종 판정과 자동 후보의 관계를 기록한다.
5. 보고서가 어떤 분석 실행과 전문가 판정을 사용했는지 재현할 수 있게 연결한다.

#### 보고서 발행

1. 승인 전 필수 데이터와 권한을 다시 확인한다.
2. 초안을 생성하고 시각·내용 검수를 수행한다.
3. 승인된 판본에 발행 정보를 부여한다.
4. 고객은 짧은 수명의 권한 확인된 링크 또는 동등한 안전한 방식으로 접근한다.
5. 개정·회수는 기존 발행본을 덮어쓰지 않고 새 이력으로 처리한다.

### 2.8 운영·관찰 가능성

- 업로드, 메타데이터 추출, 분석, 보고서와 알림의 대기·실행·실패를 구분한다.
- 사용자가 재시도를 이해할 수 있는 오류와 운영자용 진단 정보를 분리한다.
- 원본 체크섬 불일치, 권한 거부, 반복 실패와 비정상 다운로드를 관찰할 수 있게 한다.
- 로그에 원본 이미지, 개인정보, 토큰과 서명 URL 전체를 남기지 않는다.
- 백업 성공만이 아니라 복원 시험 결과를 기록할 수 있게 한다.

### 2.9 호환성·확장성과 이전 가능성

#### 프론트엔드와 배포

- 표준 웹 API와 재현 가능한 빌드 산출물을 우선하고, Cloudflare에만 있는 API는 별도 어댑터 또는 얇은 엣지 계층에 격리한다.
- 업무 화면은 배포 제공자의 전역 객체·파일시스템·런타임 제한을 직접 가정하지 않는다.
- 사이트 주소, API 기준 주소, Storage 주소, 인증 콜백, 작업 서버와 기능 플래그를 환경별 설정으로 주입한다.
- 직접 URL 새로고침, 라우팅, 보안 헤더, CORS와 인증 콜백을 배포 제공자별 회귀검사 대상으로 둔다.
- 사용자 소유 도메인과 DNS를 애플리케이션 호스트와 분리해, 이전 시 도메인을 유지하고 원본 대상만 바꿀 수 있게 한다.

#### 데이터베이스와 인증

- 업무 데이터와 관계는 표준 PostgreSQL에서 재현 가능한 변경 이력으로 관리한다.
- Supabase Auth, RLS, Data API, Storage와 Queue에 특화된 설정은 핵심 업무 규칙과 분리해 별도 배포·검증 단위로 둔다.
- 화면이 Supabase 응답 모양을 그대로 업무 모델로 사용하지 않도록 데이터 접근 계층에서 변환한다.
- 조직·역할 정보의 원본과 권한 규칙을 문서화해 다른 인증 제공자로 옮길 때 사용자와 조직 관계를 다시 만들 수 있게 한다.
- 신규 테이블의 Data API 노출과 권한은 기본값을 추정하지 않고 명시적으로 관리하며, RLS와 Data API 권한을 별도 검증한다.

#### 파일 저장소

- 업무 데이터는 파일의 공급자 URL 대신 공급자와 무관한 논리 식별자를 참조한다.
- 객체 경로, 원본 파일명, 크기, 형식, 체크섬, 조직, 생성 원본과 파생 관계를 반출 가능한 manifest로 유지한다.
- 만료되는 서명 URL은 요청 시 생성하며 DB·보고서·알림에 영구 주소처럼 저장하지 않는다.
- Storage의 일괄 반출·재업로드와 체크섬 전수 대조 절차를 마련하고, DB 백업과 파일 백업을 별도로 수행한다.

#### 비동기 작업과 이미지 처리

- 작업 요청과 결과의 계약을 공급자 큐와 분리하고, 동일 작업의 중복 실행을 막는 논리 키를 유지한다.
- Cloudflare 또는 Supabase의 짧은 함수는 인증·웹훅·작업 전달 어댑터로 제한한다.
- 무거운 처리는 표준 컨테이너로 실행 가능한 별도 작업 서비스에 두어 다른 클라우드나 자체 서버로 옮길 수 있게 한다.
- 처리 버전, 입력 체크섬과 결과 위치를 남겨 작업 서버가 바뀌어도 과거 보고서를 재현할 수 있게 한다.

#### 운영 설정과 이전 인계물

- 저장소에는 소스, 정확한 의존성 버전과 잠금 파일, 배포 설정, DB 변경 이력, 비밀값 없는 환경변수 예시와 운영 절차를 보관한다.
- Cloudflare 영역·DNS, GitHub 저장소, Supabase 조직·프로젝트, 작업 서버와 외부 연동 계정의 소유권·관리자·복구 방법을 기록한다.
- 비밀값은 저장하지 않고 이름, 용도, 소유자, 회전·폐기와 새 환경 재발급 절차만 inventory로 관리한다.
- 이전 전에는 기존/신규 환경을 병행하고 데이터 동결·증분 동기화·DNS 전환·검증·롤백 순서를 계획한다.
- 주요 릴리스 또는 정기 점검에서 별도 시험 환경 복원과 대체 프론트엔드 호스트 배포를 수행해 문서만 있는 이식성이 되지 않게 한다.

## 3. 추가 확인이 필요한 내용

### 3.1 파일·분석

- 카메라 제조사·모델, 파일 확장자와 방사온도 데이터의 실제 구조
- 제조사 SDK의 라이선스·운영체제·컨테이너 실행 제약
- 분석 방식, 기대 정확도, 실패 기준과 전문가에게 보일 근거
- GPU 필요 여부, 건당 처리량과 목표 처리 시간
- 원본 다운로드 허용 대상과 장기 보존 비용

### 3.2 시스템 규모

- 조직·발전소·사용자·월 검사 수와 동시성
- 파일 평균/최대 크기, 월 유입량, 보존 기간과 지역 요건
- 가용성, 장애 복구 시간과 허용 데이터 손실 목표
- 개발·검수·운영 환경 분리와 운영 주체
- 현재 사용하는 Cloudflare 제품·배포 방식과 신규 프로젝트에 재사용할 범위
- Cloudflare, GitHub, Supabase와 도메인의 계정 소유자·관리자·결제 주체
- 공급자 이전을 결정할 비용·성능·지역·지원·계약 기준과 허용 중단시간

### 3.3 외부 연동

- 알림 서비스, 도메인·메일 발신 주체와 계정 소유권
- 인버터 제조사 API, 인증 방식, 호출 제한과 데이터 권리
- 유지보수 업체와 공유할 최소 정보 및 동의 방식
- 고객 시스템으로 내보낼 파일·데이터 형식

## 4. 아키텍처 결정 게이트

1. 샘플 원본으로 메타데이터 추출과 미리보기 가능성을 검증한다.
2. 실제 규모로 업로드·저장·분석·PDF 비용을 추정한다.
3. 역할·조직·파일 경계를 위협 모델과 테스트 시나리오로 합의한다.
4. 운영 계정 소유권, 백업·복원, 장애 대응과 인계 책임을 계약에 넣는다.
5. 깨끗한 clone 재빌드, 별도 시험 프로젝트 복원과 대체 프론트엔드 호스트 배포가 가능한지 확인한다.
6. 그 뒤에 제품, 정확한 버전, 배포 단위와 실제 데이터 구조를 확정한다.
