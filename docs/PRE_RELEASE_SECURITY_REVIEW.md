# 공개 배포 전 로그인·보안·오류 점검

- 기준일: 2026-09-04
- 대상: SolarScope 운영 화면(`/`, `/admin`)과 Supabase 프로젝트 `solar-asset-care`
- 상태: 공개 배포 보류

## 현재 결론

관리자 페이지와 데이터 저장 기능은 구현돼 있지만 아직 공개 운영 승인 상태는 아니다. 코드 검사, 빌드, 익명 접근 차단과 데이터베이스 보안 진단은 통과했다. 반면 로그인 운영방식, 실제 계정 기반 역할별 시험, 고객 데이터의 소유 범위, 승인 상태 전환과 감사기록은 공개 전 결정·보강이 필요하다.

현재 공개 주소에는 기존 샘플 데모가 계속 표시된다. 새 운영형 화면은 배포하지 않고 저장된 후보 버전으로만 보관한다.

## 확인을 마친 항목

| 항목 | 결과 | 확인 내용 |
|---|---|---|
| 프론트엔드 타입·정적 검사 | 통과 | TypeScript, 정적 검사와 프로덕션 빌드 성공 |
| 열화상 상대 분석 API | 통과 | 시험 픽셀에서 고온·저온 후보를 각각 반환 |
| 익명 업무 테이블 접근 | 차단 | 로그인하지 않은 발전소 조회가 HTTP 401 |
| 익명 최초 조직 개설 | 차단 | 로그인하지 않은 개설 RPC가 HTTP 401 |
| 데이터베이스 보안 진단 | 통과 | Supabase Security Advisor 경고 0건 |
| API 키 | 통과 | 브라우저에는 `sb_publishable_...` 키만 사용하고 secret key 미사용 |
| 원본 파일 | 기반 준비 | 비공개 버킷, 조직 UUID 경로, SHA-256, 60초 서명 URL 적용 |
| 시간 | 통과 | 절대 시각은 UTC로 저장하고 화면은 `Asia/Seoul`로 표시 |
| 최초 관리자 보호 | 기반 준비 | 이메일 인증과 1회용 개설 코드가 모두 있어야 조직 소유자 생성 |

## 공개 전 반드시 결정하거나 보강할 항목

### 1. 로그인 운영방식

현재 코드는 누구나 계정을 만들 수 있지만, 조직 관리자가 권한을 연결하기 전에는 업무 데이터를 볼 수 없다. 데이터 유출로 바로 이어지는 구조는 아니지만 불필요한 계정 생성과 인증 메일 남용 가능성이 있으므로 운영 방식으로 확정하지 않는다.

관리자·현장·전문가 계정에는 다음 방식을 권장한다.

1. 조직 소유자가 이메일로 초대한다.
2. 초대받은 사용자가 이메일 인증과 비밀번호 설정을 완료한다.
3. 소유자·승인 담당자는 TOTP 방식의 2단계 인증을 사용한다.
4. 가입·로그인·비밀번호 재설정 화면에는 Cloudflare Turnstile을 적용한다.
5. 고객 로그인은 고객 데이터 소유관계가 확정된 뒤 이메일 또는 카카오·네이버 같은 별도 방식으로 결정한다.

이 방식을 적용하려면 공개 자유가입을 끄고, 관리자 초대용 서버 기능과 비밀번호 재설정 화면을 추가해야 한다.

### 2. 인증 주소와 메일

- 운영 도메인을 Supabase의 Site URL과 허용 Redirect URL에 정확히 등록해야 한다.
- 이메일 인증, 초대, 비밀번호 재설정 링크의 만료와 재사용 오류를 시험해야 한다.
- 실제 고객에게 쓰기 전에는 발신 도메인이 확인되는 전용 SMTP를 연결해야 한다.
- Supabase 프로젝트와 GitHub 계정 자체에도 MFA를 적용하고 복구 담당자를 한 명 더 지정하는 편이 안전하다.

### 3. 실제 계정 기반 수용시험

현재 Auth 사용자는 0명이다. 따라서 로그인 이후의 전체 흐름은 아직 실제 세션으로 시험하지 못했다. 최소한 다음 계정과 두 조직으로 검증해야 한다.

- 조직 소유자
- 운영 관리자
- 현장 담당자
- 판독 전문가
- 승인 담당자
- 유지보수 담당자
- 고객

각 계정에서 허용된 조회·등록·수정·다운로드가 성공하고, 허용되지 않은 동작과 다른 조직 접근이 모두 거부되는지 확인해야 한다.

### 4. 고객 데이터 범위

현재 멤버십은 조직 단위다. 같은 운영 조직에 여러 고객을 `client` 역할로 넣으면 고객이 조직 전체의 발전소·점검·보고서를 보게 될 수 있다. 고객 포털을 열기 전에 아래 둘 중 하나를 결정해야 한다.

- 고객마다 별도 조직을 만들고 운영자에게 교차 조직 업무 권한을 부여한다.
- 운영 조직 안에서 고객과 발전소의 소유관계를 별도 테이블로 만들고 고객 RLS를 발전소 단위로 제한한다.

이 결정 전에는 `client` 계정을 실제 고객에게 발급하지 않는다.

### 5. 승인·감사·오류 복구

- 현재 보고서 상태는 화면에서 변경할 수 있지만 `초안 → 검토 → 승인 → 발행` 순서를 데이터베이스가 강제하지 않는다.
- 발전소·점검·판정·보고서·유지보수의 주요 변경을 감사기록에 자동으로 남기는 트리거 또는 전용 RPC가 필요하다.
- 파일 저장 후 분석 결과 저장이 실패하면 원본만 남을 수 있다. 재시도 상태와 부분 성공 안내를 분리해야 한다.
- 조직의 마지막 소유자를 삭제하거나 스스로 강등해 관리자가 사라지는 상황을 데이터베이스에서 차단해야 한다.
- 보고서 발행본은 화면 인쇄뿐 아니라 변경 불가능한 PDF 파일과 체크섬으로 보관해야 한다.

### 6. 파일과 분석 API 보호

- 현재 상대 분석 API는 데모에서도 사용하므로 로그인 없이 호출할 수 있다. 공개 전에는 인증 전용 API와 제한된 데모 분석을 분리하거나 Cloudflare에서 요청 횟수를 제한해야 한다.
- 브라우저가 보낸 MIME 형식만 신뢰하지 말고 실제 파일 시그니처와 이미지 디코딩 성공 여부를 검사해야 한다.
- 큰 열화상 원본은 네트워크 중단 후 재개할 수 있는 TUS 방식 업로드로 전환해야 한다.
- TIFF·카메라 원본은 제조사별 샘플로 크기, 메타데이터와 악성 파일 처리 시험을 해야 한다.

## 권장 진행 순서

1. 관리자 로그인 방식을 `초대 전용 이메일 + 이메일 인증 + 소유자·승인자 MFA`로 확정한다.
2. 운영 도메인, Redirect URL, Turnstile, SMTP와 비밀번호 재설정을 설정한다.
3. 고객 조직 모델을 확정하고 고객용 RLS를 분리한다.
4. 승인 상태 전환, 감사기록, 마지막 소유자 보호와 부분 실패 복구를 데이터베이스에 추가한다.
5. 실제 시험 계정과 두 조직으로 역할별 허용·거부 시험을 수행한다.
6. 열화상 JPG·PNG와 카메라 원본 샘플로 업로드·재시도·분석·보고서 전 과정을 시험한다.
7. 모든 차단 항목을 통과한 저장 버전만 공개 배포한다.

## 배포 승인 기준

다음 조건을 모두 만족할 때만 공개 배포를 요청한다.

- 로그인 방식과 고객 조직 모델 확정
- Auth 운영 URL·메일·봇 방지·MFA 설정 완료
- 역할별 실제 계정 시험 통과
- 다른 조직과 고객 간 데이터·파일 격리 시험 통과
- 승인 순서·감사기록·오류 복구 시험 통과
- 대용량 원본 업로드와 백업·복원 절차 확인
- 공개 배포에 대한 사용자의 별도 승인
