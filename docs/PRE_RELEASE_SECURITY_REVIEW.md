# 공개 배포 전 로그인·보안·오류 점검

- 기준일: 2026-09-04
- 대상: SolarScope 운영 화면(`/`, `/admin`)과 Supabase 프로젝트 `solar-asset-care`
- 상태: 공개 배포 보류

## 현재 결론

관리자·전문가·의뢰인 3개 역할과 데이터 저장 기능은 구현돼 있지만 아직 공개 운영 승인 상태는 아니다. 의뢰인 공개 가입, 관리자 초대, 발전소별 의뢰인 소유권, 전문가별 점검 배정, 마지막 관리자 보호와 익명 접근 차단은 적용했다. 코드 검사, 빌드와 Supabase 보안 진단도 통과했다. 실제 메일·계정 기반 수용시험, 운영 도메인, 비밀번호 복구·MFA·봇 방지, 승인 순서와 전체 감사기록은 공개 전에 보강해야 한다.

현재 공개 주소에는 기존 샘플 데모가 계속 표시된다. 새 운영형 화면은 배포하지 않고 저장된 후보 버전으로만 보관한다.

## 공개 전 반드시 결정하거나 보강할 항목

### 1. 로그인 운영방식

운영 방식은 다음처럼 확정해 코드와 데이터 권한에 반영했다.

1. 의뢰인은 사이트에서 직접 가입하고 이메일 인증 후 의뢰인 권한을 연결한다.
2. 전문가는 관리자가 이메일로 초대한다.
3. 추가 관리자는 기존 관리자가 이메일로 초대한다.
4. 관리자는 세 역할과 계정의 초대 대기·사용 중·사용 중지 상태를 변경한다.

아직 비밀번호 재설정 화면, 관리자 MFA와 Cloudflare Turnstile은 구현하지 않았다. Supabase 기본 메일은 개발 확인용이므로 실제 고객 초대 전 전용 SMTP도 필요하다.

### 2. 인증 주소와 메일

- 운영 도메인을 Supabase의 Site URL과 허용 Redirect URL에 정확히 등록해야 한다.
- 이메일 인증, 초대, 비밀번호 재설정 링크의 만료와 재사용 오류를 시험해야 한다.
- 실제 고객에게 쓰기 전에는 발신 도메인이 확인되는 전용 SMTP를 연결해야 한다.
- Supabase 프로젝트와 GitHub 계정 자체에도 MFA를 적용하고 복구 담당자를 한 명 더 지정하는 편이 안전하다.

### 3. 실제 계정 기반 수용시험

현재 Auth 사용자는 0명이다. 따라서 로그인 이후의 전체 흐름은 아직 실제 세션으로 시험하지 못했다. 관리자 2명, 전문가 1명, 의뢰인 2명과 의뢰인별 발전소를 만들어 아래를 확인해야 한다.

- 의뢰인은 본인 발전소 등록·점검 요청·발행 보고서 열람만 가능
- 전문가는 자신에게 배정된 점검·원본·후보·보고서 초안만 작업 가능
- 관리자는 전체 데이터, 전문가 배정, 최종 승인·발행과 계정 상태 관리 가능
- 다른 의뢰인의 발전소·점검·보고서와 미배정 전문가의 원본 조회는 모두 거부
- 마지막 활성 관리자 강등·사용 중지는 거부

### 4. 고객 데이터 범위

단일 운영 조직 안에 `plant_requesters` 소유관계를 두는 방식으로 확정했다. 의뢰인 가입 시 운영 조직에는 연결되지만, 조회 범위는 연결된 발전소로 다시 제한된다. 작성 중 보고서와 원본 파일은 의뢰인에게 보이지 않고 관리자가 발행한 보고서와 채택 소견만 보인다.

관리자가 의뢰인 대신 발전소를 만들 때는 발전소 등록 화면에서 의뢰인을 선택해 함께 연결한다. 실제 계정 수용시험을 통과하기 전까지는 실제 고객 자료를 넣지 않는다.

### 5. 승인·감사·오류 복구

- 전문가는 보고서를 `초안·검토 요청`까지만 처리하고 승인·발행은 관리자만 가능하지만, `초안 → 검토 → 승인 → 발행`의 전체 전이 순서는 아직 데이터베이스가 강제하지 않는다.
- 발전소·점검·판정·보고서·유지보수의 주요 변경을 감사기록에 자동으로 남기는 트리거 또는 전용 RPC가 필요하다.
- 파일 저장 후 분석 결과 저장이 실패하면 원본만 남을 수 있다. 재시도 상태와 부분 성공 안내를 분리해야 한다.
- 마지막 활성 관리자의 강등·사용 중지는 차단했다. 관리자 계정 완전 삭제와 소유권 이전 화면은 아직 없다.
- 보고서 발행본은 화면 인쇄뿐 아니라 변경 불가능한 PDF 파일과 체크섬으로 보관해야 한다.

### 6. 파일과 분석 API 보호

- 현재 상대 분석 API는 데모에서도 사용하므로 로그인 없이 호출할 수 있다. 공개 전에는 인증 전용 API와 제한된 데모 분석을 분리하거나 Cloudflare에서 요청 횟수를 제한해야 한다.
- 브라우저가 보낸 MIME 형식만 신뢰하지 말고 실제 파일 시그니처와 이미지 디코딩 성공 여부를 검사해야 한다.
- 큰 열화상 원본은 네트워크 중단 후 재개할 수 있는 TUS 방식 업로드로 전환해야 한다.
- TIFF·카메라 원본은 제조사별 샘플로 크기, 메타데이터와 악성 파일 처리 시험을 해야 한다.

## 권장 진행 순서

1. 운영 도메인, Auth Redirect URL과 전용 SMTP를 설정하고 가입·초대 메일을 시험한다.
2. 비밀번호 재설정, 관리자 MFA와 Turnstile을 구현한다.
3. 실제 시험 계정으로 의뢰인 간·전문가 배정 간 허용·거부 시험을 수행한다.
4. 승인 상태 전환, 전체 감사기록과 파일 부분 실패 복구를 보강한다.
5. 열화상 JPG·PNG와 카메라 원본 샘플로 업로드·재시도·분석·보고서 전 과정을 시험한다.
6. 변경 불가능한 발행 PDF, 체크섬과 백업·복원 절차를 확인한다.
7. 모든 차단 항목을 통과한 저장 버전만 공개 배포한다.

## 배포 승인 기준

다음 조건을 모두 만족할 때만 공개 배포를 요청한다.

- 3개 역할과 발전소별 의뢰인 소유권 수용시험 통과
- Auth 운영 URL·메일·봇 방지·MFA 설정 완료
- 역할별 실제 계정 시험 통과
- 다른 조직과 고객 간 데이터·파일 격리 시험 통과
- 승인 순서·감사기록·오류 복구 시험 통과
- 대용량 원본 업로드와 백업·복원 절차 확인
- 공개 배포에 대한 사용자의 별도 승인
