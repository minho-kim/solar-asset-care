# 보안과 조직별 데이터 격리

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 최종 수정일: 2026-08-31
- 주의: 이 문서는 계약 및 요구사항 확정 전 보안 설계 제안이다. 실제 인증·권한 정책과 규정 준수 범위는 확정되지 않았다.

## 1. 확인된 내용

- 독립 SaaS 구조와 여러 고객 조직 지원 가능성을 고려한다.
- 고객은 자신의 발전소 보고서와 조치 권고만 볼 수 있어야 한다.
- 원본·분석 파생물·전문가 판정·보고서 개정 이력을 보존해야 한다.
- API 토큰과 자격증명을 프론트엔드나 코드에 하드코딩하지 않는다.
- 데이터 내보내기, 보존, 백업·복원 계획이 필요하다.
- 관리자와 고객의 권한을 분리하고 HTTPS를 사용한다는 방향이 회의자료에 포함돼 있다.
- 사용자는 현재 다른 서비스를 `Cloudflare + GitHub + Supabase`로 운영하고 있으며, 신규 프로젝트에서도 해당 운영 경험을 초기 참고점으로 사용할 수 있다.

## 2. 계약 전 기술 제안

### 2.1 보호 대상

- 고객·발전소·설비와 담당자 정보
- 위치·촬영 조건이 포함된 열화상·가시광 원본
- 분석 후보, 전문가 판정·코멘트와 조치 권고
- 보고서 초안·발행본·개정본과 고객 열람 정보
- 유지보수 요청, 견적, 작업·완료 증빙
- 사용자 계정, 조직 소속, 역할과 승인 기록
- 인버터 자격증명과 수집 데이터(연동 시)
- 감사 로그, 내보내기 파일과 백업

### 2.2 조직 경계

- 모든 비공개 업무 데이터는 소유 조직을 식별할 수 있어야 한다.
- 브라우저의 선택 조직, 화면 필터나 숨김 처리만으로 격리하지 않는다.
- 사용자가 요청한 대상이 현재 조직에 속하고 해당 역할의 행위가 허용되는지 서버·데이터 계층에서 확인한다.
- 조직을 확인할 수 없는 요청은 다른 조직의 기본값이 아니라 거부 또는 빈 결과로 처리한다.
- 자식 대상의 식별자만 알고 직접 요청해도 상위 조직 관계를 다시 검증한다.
- 운영자 교차 조직 접근이 필요하면 일반 관리자와 분리하고 목적·범위·감사 조건을 계약에서 정한다.

Supabase를 사용할 경우 RLS로 행 접근을 통제하고, 필요한 역할에만 명시적인 Data API 권한을 부여하는 방향을 제안한다. 실제 정책, 역할과 GRANT는 계약 후 별도 보안 설계·시험을 거쳐 작성한다.

### 2.3 역할과 최소 권한

역할 후보는 운영 관리자, 촬영 담당자, 진단 전문가, 승인자, 고객 사용자, 유지보수 담당자와 제한된 시스템 작업자다. 역할별로 조회·업로드·수정·진단·승인·발행·내보내기·삭제 권한을 나누고 다음을 검토한다.

- 전문가는 배정된 검사를 보는가, 같은 조직의 모든 검사를 보는가?
- 승인자는 전문가 판정을 직접 바꿀 수 있는가, 수정 요청만 할 수 있는가?
- 고객은 원본/분석 후보를 보는가, 발행 보고서만 보는가?
- 유지보수 사업자는 고객 개인정보와 원본 중 무엇까지 필요한가?
- 운영 지원 인력의 긴급 접근은 어떻게 승인·종료·감사하는가?

메뉴를 숨기는 것과 권한 차단을 혼동하지 않는다. 직접 URL, API 호출과 파일 링크에서도 같은 권한이 적용돼야 한다.

### 2.4 파일 보안

- 원본, 파생물과 보고서는 기본 비공개로 제안한다.
- 저장 경로에도 조직 경계를 반영하되 경로 문자열만 신뢰하지 않고 다운로드 시 권한을 다시 확인한다.
- 짧은 수명의 서명 URL 또는 동등한 방식으로 다운로드를 허용하고 만료·재발급·권한 회수 후 동작을 시험한다.
- 파일명, 메타데이터와 미리보기에도 다른 고객의 정보가 노출되지 않게 한다.
- 원본 체크섬과 업로드 완료 상태를 확인하고 원본 변경·덮어쓰기를 제한한다.
- 내보내기 파일은 생성 범위, 요청자, 만료와 다운로드 이력을 연결한다.

### 2.5 키·자격증명

- 브라우저·정적 클라이언트에는 publishable key만 사용한다.
- 비밀 키, 외부 API 토큰, 서비스 자격증명은 서버 측 비밀 저장소에서 최소 권한으로 관리한다.
- 로그, 오류 메시지, 분석 결과와 보고서에 토큰·서명 URL 전체가 남지 않게 한다.
- 발급 주체, 소유자, 사용 환경, 회전 주기, 만료·회수와 계약 종료 시 폐기를 정한다.
- Supabase 의존성·인증 방식을 구현 단계에서 바꿀 경우 공식 현재 문서와 changelog를 확인하고 정확한 패키지 버전을 고정한다.

### 2.6 감사와 변경 이력

다음 행위는 행위자, 조직, 대상, 시점, 결과와 필요한 변경 이유를 추적하는 후보로 제안한다.

- 원본 업로드 완료·무효·대체와 다운로드
- 이미지 짝 자동 결과의 수동 수정
- 분석 실행·재실행과 사용 결과 선택
- 전문가 판정·주석·조치 권고 변경
- 보고서 승인·반려·발행·개정·회수
- 고객/사업자 권한 부여·회수와 중요 내보내기
- 인버터 자격증명 연결·갱신·회수
- 보존 예외, 삭제와 복원

민감한 원문 전체를 감사 로그에 복제하기보다 변경 식별과 안전한 차이 기록 방식을 설계한다. 감사 기록 자체의 조회 권한과 보존 기간도 정한다.

### 2.7 개인정보·시설 정보

- 수집 목적과 최소 필요 정보를 역할별로 정의한다.
- 위치 정보, 원본 이미지와 연락처가 시설 보안 또는 개인정보에 해당하는지 분류한다.
- 유지보수 업체 등 제3자 제공의 목적, 동의·계약 근거와 회수 절차를 정한다.
- 보고서·내보내기·알림에 표시할 개인정보를 최소화한다.
- 보존 기간 종료, 계약 종료, 법적 보존과 분쟁 보류가 충돌할 때의 절차를 정한다.

### 2.8 백업·복원과 연속성

- 업무 데이터, 원본/파생 파일, 보고서와 핵심 설정의 백업 책임을 구분한다.
- 목표 복구 시간과 허용 데이터 손실량은 사용량·비용과 함께 계약에서 정한다.
- 백업 성공 로그만 보지 않고 정기적으로 별도 환경에 복원해 완전성과 권한을 확인한다.
- 파일과 관계 데이터의 시점이 어긋난 복원, 진행 중 업로드와 분석 작업을 고려한다.
- 계정·도메인·저장소·백업 위치와 복구 문서를 발주/운영 주체가 인계받을 수 있게 한다.

### 2.9 기본 위협 시나리오

- 다른 조직의 식별자를 주소나 요청에 넣어 조회·수정
- 만료 전 공유된 파일 링크를 권한 회수 후 재사용
- 고객 사용자가 승인 전 초안·원본에 접근
- 전문가가 배정되지 않은 검사 판정을 변경
- 업로드 파일의 위장 형식·손상·악성 콘텐츠
- 중복 클릭으로 보고서가 여러 번 발행되거나 알림이 반복됨
- 로그·분석 작업·오류 화면에 비밀정보가 노출됨
- 백업 복원 후 조직 경계 또는 최신 권한이 잘못 적용됨

### 2.10 공급자 이전과 보안 연속성

- Cloudflare, GitHub, Supabase, 도메인과 작업 서버 계정은 조직 명의·관리자·복구수단·결제 주체를 확인하고 개인 계정에만 의존하지 않는다.
- 공급자 프로젝트 주소, 영역 식별자와 비밀값은 코드·DB·보고서에 고정하지 않는다. 비밀값 없는 설정 예시와 새 환경 재발급 절차를 유지한다.
- 데이터베이스 백업과 Storage 객체 백업을 분리하고, 객체 manifest의 경로·크기·형식·체크섬과 조직 소속을 함께 보존한다.
- 인증 사용자, 조직 멤버십, 역할과 권한의 관계를 공급자와 무관한 개념으로 문서화한다. 이전 시 비밀번호를 직접 반출할 수 없는 경우 재로그인·재설정·세션 강제 만료 절차를 준비한다.
- 서명 URL, 일회성 업로드 URL과 캐시 주소는 이전 대상 데이터로 취급하지 않고 새 환경에서 다시 발급한다.
- DNS 전환 전 기존·신규 환경의 HTTPS, CORS, 인증 콜백, 보안 헤더, 조직 격리와 파일 권한을 병행 검증한다.
- 신규 환경 복원이 확인되기 전에는 기존 환경·백업·키를 해지하지 않는다. 전환 후에는 사용하지 않는 키·세션·웹훅·서비스 계정을 명시적으로 폐기한다.
- 이전용 백업도 실제 고객 데이터와 같은 접근통제·암호화·보존·파기 정책을 적용한다.

## 3. 추가 확인이 필요한 내용

- 고객·운영자·전문가·사업자의 실제 역할과 겸임/분리 원칙
- 공개 대상 자료와 익명 접근이 필요한 기능의 존재 여부
- 개인정보처리자, 위탁·제3자 제공과 국외 저장/처리 제한
- 계정 인증 방식, 다중 인증과 퇴사·계약 종료 시 권한 회수 시간
- 원본·보고서·감사 로그·백업의 보존·파기 기간
- 고객의 데이터 내보내기·삭제 요청 범위와 형식
- 운영 지원자의 긴급 접근 및 사고 통지 절차
- 가용성, 복구 목표, 백업 빈도와 복원 시험 주기
- 보안 점검, 취약점 대응, 하자보수와 유지보수 책임
- 제조사 API 약관, 토큰 소유권과 데이터 재사용 권리
- Cloudflare 영역·GitHub 저장소·Supabase 조직/프로젝트와 도메인의 실제 소유자·복구 관리자
- 각 공급자의 데이터 저장 지역, 반출 형식·비용·속도와 계약 종료 후 삭제 증빙
- 공급자 이전 시 허용 중단시간, 인증 사용자 재로그인 정책과 기존 링크 만료 처리

## 4. 계약 전 보안 산출물 권고

- 역할·행위·데이터 범위 권한표
- 두 조직 이상을 사용한 교차 접근 시험 시나리오
- 파일 분류·보존·다운로드와 내보내기 정책
- 키·외부 계정 소유권과 회전/폐기 절차
- 위협 모델과 보안 수용 기준
- 백업·복원·장애 대응과 인계 절차
- 공급자별 설정 inventory, 데이터 반출 manifest와 대체 환경 복원·전환·롤백 절차
