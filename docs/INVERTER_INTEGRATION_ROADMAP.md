# 인버터 데이터 연동 로드맵

- 상태: 계약 전 준비 초안
- 작성일: 2026-08-25
- 주의: 이 문서는 계약 및 요구사항 확정 전 단계 제안이다. 제조사 API 제공 여부, 인증, 데이터 항목과 호출 제한은 확인되지 않았다.

## 1. 확인된 내용

- 인버터 데이터는 열화상 진단의 보조 자료로 유용할 수 있다.
- 최초 MVP 필수 기능으로 확정하지 않고 기존 거래처를 대상으로 한 2단계 이후 과제로 검토한다.
- 발전소 전체 발전량만으로는 특정 모듈 고장 위치를 판단하기 어렵다.
- 열화상 위치와 발전 데이터를 연결하려면 인버터 → MPPT → 스트링 → 모듈의 연결 관계가 필요하다.
- 제조사마다 인증, 데이터, 상태 표현, 호출 제한과 계정 권한이 다르다.

## 2. 계약 전 기술 제안

### 2.1 단계별 접근

#### 준비 단계 - 거래처·장비 조사

- 기존 거래처별 인버터 제조사, 모델, 설치 시기와 통신 방식을 조사한다.
- 계정 소유자, 데이터 접근 동의, API 제공 여부와 파트너 자격을 확인한다.
- 설비 연결도와 장비 교체 이력의 존재 여부를 확인한다.
- 공식 문서, 샘플 응답, 호출 제한, 과거 데이터 범위와 비용을 확보한다.

**진입 조건:** 우선순위 제조사와 실제 계정 권한, 대표 발전소 샘플이 확인돼야 한다.

#### 1단계 - 수동 자료 활용

- CSV·엑셀·기존 보고서 등 고객이 합법적으로 보유한 자료를 수동 업로드한다.
- 파일 출처, 기간, 타임존, 단위, 장비 범위와 누락을 사람이 확인한다.
- 열화상 진단 화면에서 참고 자료로 연결하되 자동 고장 판정에는 사용하지 않는다.

**목표:** API 계약 없이도 필요한 데이터와 현장 업무 가치를 확인한다.

#### 2단계 - 단일 제조사 공식 API

- 거래처 보급량과 문서 품질이 높은 제조사 한 곳을 우선한다.
- 인증·권한 회수·토큰 만료, 호출 제한과 장애 처리를 검증한다.
- 원본 응답 보존 범위와 업무용 공통 표현을 분리한다.
- 중복 수집, 지연 도착과 재수집에도 같은 시계열 구간이 안전하게 처리되게 한다.

**목표:** 운영 가능한 수집·재시도·권한 모델을 한 제조사에서 증명한다.

#### 3단계 - 제조사별 커넥터와 공통 구조

- 제조사별 인증과 응답 해석은 각 커넥터에 격리한다.
- 발전소, 장비, 측정 종류, 시각, 값·단위, 품질과 원본 출처를 공통 개념으로 정규화한다.
- 제조사 고유 오류 코드는 원문과 해석을 함께 유지하고 억지로 하나의 상태로 합치지 않는다.
- 장비 교체·재배선과 타임존 변경을 이력으로 처리한다.

**목표:** 새 제조사를 추가해도 기존 진단·화면이 특정 API 형식에 종속되지 않게 한다.

#### 4단계 - 열화상·시계열 상관분석

- 열화상 촬영 시점 전후의 발전·전기·온도·경보 데이터를 연결한다.
- 설비 연결 구조와 데이터 품질을 확인한 경우에만 모듈/스트링 수준의 상관분석을 시도한다.
- 결과는 인과관계나 고장 확정이 아니라 전문가가 검토할 보조 근거로 제시한다.

**목표:** 진단 우선순위와 판정 근거를 보강하되 사람의 최종 책임을 유지한다.

### 2.2 검토할 데이터 범주

공식 API가 제공하고 사용 권한이 확인될 때 다음 범주를 검토한다.

- 발전량, 현재 전력과 누적값
- DC·AC 전압과 전류
- MPPT·스트링 수준 측정값
- 인버터 온도
- 경보·오류 원문과 발생/해제 시각
- 통신 상태와 데이터 품질
- 장비·발전소 식별과 시간 기준

실제 컬럼명, 상태값, 요청 파라미터와 단위는 공식 문서·샘플 응답을 확인한 뒤 결정한다.

### 2.3 수집·정규화 원칙

- 수집 시각과 장비 측정 시각을 구분한다.
- 타임존과 일광절약시간 적용 여부를 명시적으로 관리한다.
- 누락, 통신 끊김, 지연·역순 도착과 장비 교체를 정상적인 운영 상황으로 본다.
- 원시 데이터의 출처와 변환/집계 방법을 재현할 수 있게 한다.
- 동일 기간 재수집이 중복값을 만들지 않도록 멱등성을 확보한다.
- 제조사 호출 제한을 존중하고 지수적 대기 또는 공식 권고에 맞는 재시도를 사용한다.
- 시계열 파티셔닝·집계 주기는 실제 유입량과 조회 패턴을 측정한 뒤 결정한다.

### 2.4 보안·권한 원칙

- API 토큰과 자격증명은 프론트엔드·저장소·로그에 노출하지 않는다.
- 가능한 경우 고객 또는 조합 명의의 공식 계정과 최소 읽기 권한을 사용한다.
- 토큰 발급, 보관, 회전, 만료, 권한 회수와 계약 종료 시 폐기 책임을 정한다.
- 고객이 허용한 발전소·기간·데이터만 수집하고 조직 간 재사용하지 않는다.
- 외부 사업자 약관, 데이터 재사용·보관과 보고서 포함 권한을 확인한다.

## 3. 추가 확인이 필요한 내용

### 3.1 거래처 조사표에 필요한 질문

- 제조사, 모델, 펌웨어, 게이트웨이/로거와 통신 방식
- 발전소별 인버터·MPPT·스트링·모듈 연결도
- 계정 소유자, 관리자 권한과 제3자 데이터 제공 동의
- 공식 API/내보내기 기능, 파트너 등록과 비용
- 실시간·과거 데이터 범위, 해상도, 보존 기간과 호출 제한
- 장비 식별자 안정성, 교체·재배선 이력
- 타임존, 단위, 경보 코드 문서와 샘플 응답

### 3.2 단계 전환 판단

- 수동 자료가 실제 진단 판단을 얼마나 개선했는가?
- 우선 제조사 하나가 거래처의 충분한 비중을 차지하는가?
- 공식 API 사용 권한과 운영 계정 소유권이 명확한가?
- 데이터 누락률과 설비 연결 정보가 상관분석에 충분한가?
- 수집·저장·지원 비용이 고객 가치에 비례하는가?

## 4. 최초 MVP 제외 권고

- 여러 제조사 동시 연동
- 초 단위 실시간 대규모 관제
- 인버터 데이터만으로 특정 모듈 고장 위치 자동 확정
- 자동 예지 정비와 무인 조치 결정
- 문서가 없는 비공식/역공학 API 사용
